# macbench —— Mac 电池状态性能对比跑分工具

一个**零依赖**的 shell 脚本(只需 macOS 自带的 clang 和系统命令),用于对比
**电池正常**和**电池故障/缺失**两种状态下 Mac 的真实性能差异。

针对 Intel 和 Apple Silicon **分别提供两个脚本**,各自的指标和判读逻辑
按架构特点单独设计:

| 脚本 | 适用机型 | 特色 |
|------|---------|------|
| [macbench-apple.sh](macbench-apple.sh) | M1/M2/M3/M4 | P/E 核心识别、**持续性能曲线**、QoS 优先派发性能核 |
| [macbench-intel.sh](macbench-intel.sh) | Intel | 标称/睿频基准、实际频率对照、XCPM 热节流等级 |
| [macbench.sh](macbench.sh) | 两者(原型) | 最初的通用版,保留作参考,建议改用上面两个 |

两个脚本互不通用,选错了会直接提示(不会跑出错的结果)。

---

## 为什么电池坏了会影响性能?

Mac 的电源管理系统把电池当作供电系统的一部分。当电池故障、被识别为失效或
缺失时,即使插着充电器,macOS 也可能认为供电能力不足,从而:

1. **主动降频**:`CPU_Speed_Limit` 被压到 50%(甚至更低),CPU 只允许跑一半速度;
2. **禁用睿频 (Turbo Boost)**:满载时无法冲到最高频率;
3. 部分机型还会限制 GPU 性能。

本脚本把**限速状态**和**实际计算性能**放在同一次运行里记录,两次运行即可对比。

---

## 快速开始

```bash
chmod +x macbench-apple.sh macbench-intel.sh

# Apple Silicon (M1/M2/M3/M4)
./macbench-apple.sh

# Intel Mac
./macbench-intel.sh
```

脚本会:显示机型/芯片/核心信息 → 检查供电状态(电池供电会警告) →
读取电池健康(循环次数、健康度、永久故障) → 读取限速状态 →
请你给测试命名 → 跑分 → 结果存到 `results/result_时间戳.txt`。

Apple 版默认还会跑一段 **30 秒持续性能曲线**(`--sustain 60` 可延长到 60 秒,
`--quick` 模式缩短为 6 秒)。

---

## 对比两次测试

在**两种状态下各跑一次**(中间不改变其他条件),然后:

```bash
./macbench-apple.sh compare results/result_旧.txt results/result_新.txt
./macbench-intel.sh compare results/result_旧.txt results/result_新.txt
```

### 如何判读结果

| 现象 | 结论 |
|------|------|
| 单核/多核比值 ≈ 0.50 | 性能被限制了一半,典型的无电池降频 |
| 多核比值明显低于单核比值 | 睿频被禁用,或部分核心被限制 |
| `CPU_SPEED_LIMIT < 100` | **强证据**:macOS 明确报告了主动限速 |
| 内存带宽比值 ≈ 1.0 | 内存未被限制(正常现象,降频主要影响 CPU) |
| 所有比值 ≈ 1.0 且无限速 | 两种状态性能无差别 |

**关于 `CPU_Speed_Limit` 的严谨说明**(重要):

- `CPU_Speed_Limit < 100` 是 macOS 自我报告的主动限速,属于**强证据**;
- 但反过来不成立:该字段**缺失或显示 100% 时,不能单独排除**其他形式的
  功耗/温度/频率管理 —— 只能说明"macOS 没有报告传统意义上的限速";
- Apple Silicon 上尤其如此,所以 Apple 版额外提供两个交叉验证手段:
  - **持续性能曲线**(`SUSTAIN_MIN_RATIO`):满载 30~60 秒分段统计吞吐量,
    区分"一直被限速"和"跑久后因温度/功耗管理逐渐下降";
  - `--freq`:用 `powermetrics` 看 P/E 集群的实际运行频率和功耗。

**关于小幅差异**:分数有正常的运行间波动。比值在 0.95~1.05 之间建议视为
噪声;像"正常 100 vs 异常 94"这种 -6% 的小幅差异,需要先在**同一状态**
连跑两次确认测试本身稳定(比值也在 0.95~1.05 内),再下结论。
真正有意义的证据是数量级差异(如 100 → 51)配合系统自报告的限速字段。

## 两个版本各自的观测手段

### Apple Silicon (macbench-apple.sh)

- **P/E 核心拓扑**:`hw.perflevel0/1.physicalcpu` 识别性能核与能效核数量
  (Apple Silicon 不提供 `hw.cpufrequency_max`,这是平台特性,不是缺陷);
- **QoS 调度**:测试线程设为 `QOS_CLASS_USER_INTERACTIVE`,让调度器
  优先派发到性能核,单核分数反映的是性能核水平;
- **持续性能曲线**:全核满载 30 秒(可调),每 10 秒一段统计相对吞吐量:

  ```text
  时间段        全核吞吐量(相对第一段)
    0s- 10s      100%
   10s- 20s      99%
   20s- 30s      96%
  ```

  曲线持平 → 持续性能稳定;逐段下滑 → 存在温度/功耗管理。
  这能回答"你的 M 系列是一直被限制,还是只是跑久以后才下降";
- **电池健康度**:`NominalChargeCapacity / DesignCapacity`(部分老机型
  回退用 `AppleRawMaxCapacity` / `MaxCapacity`)。

### Intel (macbench-intel.sh)

- **标称最高频率**:`hw.cpufrequency_max`,作为睿频判断基准;
- **实际频率**(`--freq`):`powermetrics` 读满载平均实际频率,
  与标称对照即可观察"限速 → 频率下降"的对应关系
  (例如 i5-7360U 标称 2.3GHz / 睿频 3.6GHz,实测只有 1.2GHz = 确认降频);
- **XCPM 热节流等级**:`machdep.xcpm.cpu_thermal_level` / `io_thermal_level`,
  非 0 表示有热压力(仅观测,不单独用于定论)。

Intel 平台的限速链路成熟,三件事可以直接互相应证:
`CPU_Speed_Limit 压低 → 实际频率下降 → 跑分下降`。

## 所有选项

| 命令 | 作用 | 耗时 |
|------|------|------|
| `./macbench-apple.sh` | Apple Silicon 正常跑分 + 30s 持续曲线 | 约 1 分钟 |
| `./macbench-apple.sh --sustain 60` | 持续曲线延长到 60 秒 | 约 1.5 分钟 |
| `./macbench-apple.sh --freq` | 额外读 P/E 集群频率与功耗(sudo) | 约 1.5 分钟 |
| `./macbench-intel.sh` | Intel 正常跑分 | 约 30 秒 |
| `./macbench-intel.sh --freq` | 额外读实际频率,对照标称睿频(sudo) | 约 40 秒 |
| 两者通用:`--auto` | 跳过交互(电池供电时不再询问) | — |
| 两者通用:`--quick` | 快速验证脚本可用,**分数不能用于对比** | 约 15 秒 / 8 秒 |
| 两者通用:`compare 旧 新` | 对比两次结果 | 瞬间 |

## 测试原理(供技术验证)

- **测试程序**:运行时用系统 clang 临时编译一个小 C 程序(`cc -O2`),
  三项测试分别是:
  - **单核**:1 个线程,固定时间预算内循环执行"双浮点递推 + 整数位运算
    混合负载",统计完成的总迭代数;
  - **多核/全核**:同上,但线程数 = CPU 核心数;
  - **内存**:256 MB 缓冲区反复 `memcpy`,统计总带宽 GB/s
    (每轮修改源缓冲并读取目标缓冲,防止被优化掉);
- **防作弊**:所有线程的计算结果写入**线程私有**的 sink 变量(不共享,
  无 data race),主线程 join 后再汇总,确保编译器无法优化掉计算;
- **计时**:用 `CLOCK_MONOTONIC_RAW` 单调时钟,不受系统时间调整影响;
- **分数定义**:单核/多核分数 = 每秒完成迭代数 ÷ 10⁸ × 100,
  同一台机器上直接对比即可,跨机器对比分数没有意义;
- **持续曲线实现**:每个线程维护私有的分段计数数组,join 后汇总,
  统计每段的相对吞吐量;
- **误差来源**:后台程序、散热状态、电源模式。对比前请保持两次测试条件一致。

所有中间数据(限速状态、电池信息、原始迭代数、分段吞吐量)都写进结果文件,
任何人都可以用相同脚本复现验证。

## 安全性说明

- 脚本**不需要安装任何软件**,只用 macOS 自带的 `cc`、`pmset`、`ioreg`、
  `sysctl`、`awk` 等系统工具;
- 唯一需要密码的地方是可选的 `--freq` 模式,用 `sudo` 运行
  `powermetrics`(只读的系统性能采样工具,macOS 官方自带);
- 脚本不访问网络、不修改任何系统设置、只写入两个位置:
  脚本目录下的 `results/` 和系统临时目录(自动清理);
- 测试程序源码以明文嵌在脚本里,可自行审阅;
- 对比模式对输入数值做了合法性过滤,只接受纯数字。

## 常见问题

**Q: 我的 Mac 应该用哪个脚本?**
A: `sysctl -n machdep.cpu.brand_string` 输出以 `Apple M` 开头 → 用 apple 版;
否则 → 用 intel 版。选错时脚本会直接拒绝运行并提示。

**Q: M 系列上没有"标称最高频率"显示?**
A: Apple Silicon 不提供该系统值,Apple 版因此改用 P/E 拓扑 + 持续曲线 +
`--freq` 实际频率来判断,不再依赖这个字段。

**Q: 为什么拆成两个脚本?**
A: 两套架构的频率管理机制完全不同:Intel 可以直接观察
"限速 → 频率下降 → 分数下降"的对应链路;Apple Silicon 没有 MHz 标称值,
核心异构(P/E),需要 QoS 调度和持续性能曲线才能看清真实性能。
一个脚本同时兼容两者会让指标解释变得含糊。

**Q: 为什么不用 Geekbench?**
A: Geekbench 结果更全面,但需要下载安装、分数受版本影响、不易脚本化对比。
本脚本针对"电池状态对比"定制:把限速状态和跑分绑定记录,直接输出比值。

**Q: 跑分和对比是同一台机器才有效吗?**
A: 是。分数只用于**同一台机器前后对比**,跨机器比较没有意义。

**Q: 测试时必须插着电源吗?**
A: 对比"坏电池接电源"和"换电池后接电源"时,两次都插电源,保持一致即可。
如果单独想测"电池供电性能",脚本也会记录供电状态,但注意苹果对电池供电
本身也可能有性能管理策略。
